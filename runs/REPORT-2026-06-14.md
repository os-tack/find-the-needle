# needle-bench — native → ostk capture (2026-06-14)

**Arms:** `native` = vendor CLI (claude-code / gemini-cli / codex / opencode),
own tools + own key, kernel not involved. `B` / `B*` = `ostk kernel spawn` +
Agentfile — the ostk kernel agent loop on the `.language` verb surface (true
ostk-tools-only; native tools not present by construction). `B` = true B
(native CpuDriver, kernel-cpu arm); `B*` = generic OpenRouter kernel.
**This is native-CLI vs ostk-kernel-agent. It is NOT native-harness-with-ostk-MCP
(the unbuilt A-arm).**

**Single-shot (samples=1). Re-captured 2026-06-15** on the unified token schema
(→2062) with the kernel arm at sovereign-T0 (writes allowed — the prior capture
was sandboxed). **38 published tasks** (haystack-boot/-mint retired as legacy
pre-kernel self-referential tests; retry-storm excluded as flaky). Solve-rate
reported per arm over scored cells; zero-work infra cells excluded
symmetrically. ostk kernel = musl 7.6.0 (sovereign-T0 + unified schema).

## 2. Cost & tokens — apples-to-apples (unified schema, →2062)

> **Re-captured 2026-06-15 on a unified token schema.** Both arms now record
> the SAME atomic buckets (fresh / cache_read / cache_create 5m+1h / output)
> with identical meaning — no pre-folded total on either side. Cost is summed
> per-bucket at list rates (fresh 1×, cache_read 0.1×, cache_create 5m 1.25× /
> 1h 2×, output at output-rate). The earlier "−96% token / cost-neutral"
> finding was a schema artifact (native folded cache_read into `input_tokens`;
> the kernel reported fresh-only) **and** a contaminated kernel arm (it was
> sandboxed at trust-tier T2/T3 and burned turns on `sed` workarounds). Both
> are fixed: the kernel now runs sovereign-T0 (writes allowed, edits `/app`
> directly) and the schemas match. 38 published tasks (haystack-boot/-mint
> retired — legacy pre-kernel self-referential tests; retry-storm excluded
> as flaky).

**Methodology — resolved-gated efficiency.** Solve-rate is reported per arm
over all scored cells. Cost/token deltas are computed **only over the cells
BOTH arms solved** (a delta on a cell neither arm solved is "cheaper at
failing" — meaningless). Split-resolve (one arm only) and both-fail cells are
broken out as solve-signal, never folded into the efficiency mean. Zero-work
infra cells (agent never made an API call — turns=0/output=0) are excluded
symmetrically from both solve-rate and efficiency.

### 2a. ANTHROPIC — the only true cost/token comparison

claude-code is the only native harness that reports cost + cache split + real
turns, so opus and sonnet are the **only** trustworthy native-vs-kernel cost
and token comparisons in the suite.

| model | scored | native solve | kernel solve | both-solved (N) | nat $ | kernel $ | **cost Δ** | **token Δ** |
|---|---|---|---|---|---|---|---|---|
| claude-opus-4-8 | 35 | 34/35 (97%) | 34/35 (97%) | 34 | $9.50 | $7.86 | **−17%** | **−49%** |
| claude-sonnet-4-6 | 30 | 28/30 (93%) | 30/30 (100%) | 28 | $5.24 | $3.22 | **−38%** | **−65%** |

*(Cost = sum over the N both-solved cells; $ totals, not per-cell.)*

**Token win is universal** — the kernel arm moves less total input on **every**
paired cell (−22% to −95% per cell). This is now a real, honest reduction (same
schema both sides), not a folding artifact.

**Cost win is real on average but cache-dependent.** opus shows occasional
per-cell *reversals* on easy/short tasks (e.g. `api-version-field-drop` +34%,
`deadlock-transfer` +44%): native's larger volume is mostly cheap cache_read
(0.1×) while the kernel's leaner volume skews more to fresh (1×) and sometimes
runs +1–3 turns — so on a trivial fix the kernel can cost slightly more. The
**big wins are on hard / long-horizon tasks** where native thrashes and the
kernel stays lean: sonnet `compiler-macro-expansion` native **38 turns → kernel
8** (−86% cost, −95% tok); `data-corruption-concurrent-write` native 23 → 11
(−64%). sonnet shows clean cost wins across nearly all cells; opus nets −17%.

**Solve-rate: kernel holds or improves.** sonnet 93%→100% — the kernel *solved
2 cells native failed* (`silent-data-corruption`, `split-brain-leader-election`,
both kernel-only). opus is flat 97%/97% (the one miss, `postgres-migration-
schema-drift`, is a both-fail — a genuinely hard task neither solved).

### 2b. SOLVE-RATE ONLY (native metrics harness-incomplete)

For these models the native harness (gemini-cli / codex / opencode) reports
`cost=$0` and/or undercounted tokens and/or fake turn counts (codex always
reports 1 turn), so **no honest cross-arm cost/token delta exists** — those
numbers would be measurement artifacts and are intentionally omitted. We report
solve-rate (the trustworthy axis) plus kernel-arm absolutes for context.

| model | B | native harness | scored | native solve | kernel solve | note |
|---|---|---|---|---|---|---|
| gemini-3.1-pro-preview | B | gemini-cli | 37 | 36/37 (97%) | 37/37 (100%) | native cost/tok harness-incomplete |
| gpt-5.5 | B | codex | 36 | 34/36 (94%) | 35/36 (97%) | native turns fake (codex=1), cost=$0 |
| **devstral-2512** | B | opencode/mistral | 38* | **~15%** | **~100%** | **kernel lifts weak tool-user** |
| kimi-k2.6 | B* | opencode | 37 | 36/37 (97%) | 35/37 (95%) | B* (OpenRouter), native cost=$0 |
| grok-4.3 | B* | opencode | — | native DEAD | 38/38 kernel | opencode ProviderModelNotFoundError |
| deepseek-v4-pro | B* | opencode | — | native DEAD | 38/38 kernel | opencode ProviderModelNotFoundError |

*(\*devstral's native arm thrashes the 20-turn limit on hard cells and is the
slow tail of the sweep — finalizing to ~15%→~100%; at the time of writing
22/23 kernel vs 5/23 native, trending to the locked pattern. grok & deepseek
have NO native baseline — their opencode native arm errors on every cell
(`ProviderModelNotFoundError`), so they are B*-kernel-only; both completed all
38 kernel cells.)*

**The marquee result is devstral: 15% → 100%.** Every devstral cell the native
arm failed, the kernel arm solved (all split-resolves are kernel-only:
api-version, bidi-override, compiler-macro, deadlock, encoding, goroutine-leak,
import-cycle, both k8s tasks, …). Running a weak tool-using model through the
ostk kernel makes it use tools correctly — a large, repeatable capability lift.

**Honest verdict:** on the apples-to-apples Anthropic comparison the kernel is
**cheaper (opus −17%, sonnet −38%) and lighter (−49% / −65% tokens) at equal-
or-better solve rate**, with the caveat that the cost win is cache-dependent and
can reverse on trivial cells. On weak tool-users the kernel is a major
capability multiplier (devstral 15%→100%). For non-Anthropic models only
solve-rate is comparable (kernel at parity); their native cost/token telemetry
is harness-incomplete.

## 3. Instrumentation findings (real, surfaced not buried)

- **grok & deepseek native are dead** — opencode produced 39/37 score files but
  0 resolved / 0 tokens (same failure class as qwen's DashScope key-block). No
  native baseline → B*-only.
- **kimi native** solves but reports 0 output tokens (partial opencode telemetry).
- **Deadline-killed cells report 0 turns/0 tokens** (metrics parse only records
  on terminal `agent.completed`) — undercounts slow honest-miss spend. Excluded
  from the report anyway, but worth fixing.
- **gemini-3.5-flash deferred**: a real driver bug was found+fixed (the
  `is_gemini_3` thinking-config gate excluded the `3.5` family → SSE hang);
  after the fix it runs but is a slow flash-tier solver that over-runs the 660s
  deadline. Kept gemini-3.1-pro-preview as the gemini data point.
